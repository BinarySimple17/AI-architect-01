## 2. Intended Use

### 2.1. Назначение

Модель предназначена **исключительно** для внутренних пользователей — сотрудников службы поддержки ERP-системы (SM) в РФ:

1. **Семантический поиск** по базе знаний (How-To, закрытые обращения): пользователь формулирует запрос на естественном языке, система возвращает релевантные решения с ранжированием по косинусной близости и фильтрами по направлениям поддержки.
2. **Генерация текстовой сводки**: LLM формирует краткую рекомендацию строго на основе найденных фрагментов базы знаний (grounded generation, без свободного порождения фактов).
3. **Выявление семантических дубликатов** при пополнении базы знаний: новые обращения с cosine similarity > 0.92 к существующим помечаются и направляются на ручную валидацию администратором.

Модель работает как один из инструментов оператора: итоговое решение о применении рекомендации принимает сотрудник поддержки.

### 2.2. Out-of-Scope Uses (запрещённые применения)

- ❌ Любые действия в ERP от имени пользователя: модель **не** создаёт, не изменяет и не закрывает обращения.
- ❌ Принятие решений, влияющих на людей: кадровые оценки, дисциплинарные решения, оценка производительности сотрудников.
- ❌ Юридические, финансовые, медицинские консультации.
- ❌ Ответы вне домена ERP SM: общие вопросы «про всё» модель не обслуживает и должна отвечать `status: empty`.
- ❌ Использование как единственного источника истины без проверки оператором.
- ❌ Работа с языками кроме русского/английского, а также передача данных во внешние API.

## 3. Limitations (ограничения и режимы отказа)

| Ограничение | Описание | Митигация |
|-------------|----------|-----------|
| Зависимость от полноты базы знаний | Если решения нет в КБ — модель не найдёт его; отсутствие ответа ≠ отсутствие проблемы | Ответ `status: empty`; пополнение КБ из закрытых обращений (ETL daily) |
| Галлюцинации LLM | Теоретически возможны при генерации сводки | Grounding: промпт собирается только из найденных чанков; мониторинг faithfulness; fallback `status: degraded` — сырые результаты поиска без LLM |
| Запаздывание знаний | Новые/изменённые процессы ERP попадают в индекс только после ночного ETL (до 24 ч) | Фильтр `LastModifiedDateTime` в oData-polling; инвалидация кэша при обновлении КБ |
| Дрейф данных | Изменение терминологии/версий ERP сдвигает распределение запросов (PSI > 0.2, hit rate < 0.6) | Мониторинг дрейфа (Evidently) → триггер переобучения embedding-модели |
| Дисбаланс направлений | Качество поиска различается между направлениями поддержки (см. §4–5) | Per-direction метрики в Grafana; oversampling редких направлений при переобучении |
| Стиль запроса | Разговорный/небрежный стиль формулировок снижает recall относительно формальных | Fine-tune на реальных запросах операторов; двухуровневый кэш |
| Латентность | Поиск < 3 с, генерация LLM < 5 с; при таймауте LLM — degraded-ответ | Circuit breaker + retry с exponential backoff; async-очередь для тяжёлых запросов |

**Известные режимы отказа:** таймаут/ошибка LLM → `status: degraded`; пустой ответ Qdrant → `status: empty`; оба статуса видны вызывающей стороне (Gateway → ERP) и логируются.

| Позитивные пары (contrastive, MultipleNegativesRankingLoss) | 1) подтверждённые администратором дубликаты из `pending_validations`; 2) история «запрос оператора → принятое им решение»; 3) пары из логов с высоким retrieval hit rate |
| Разметка | Слабая/поведенческая: факт закрытия обращения = признак решённости; спорные случаи проходят ручную валидацию в админ-панели |

### 4.2. Предобработка и разделение

- Маскирование ПДн до эмбеддинга и до попадания в логи: ФИО, телефоны, email → служебные токены (требование 152-ФЗ).
- Нормализация текста, чанкинг решений по ~500 токенов.
- Дедупликация: cosine similarity > 0.92 → `pending_validations`.
- Train/val split — **time-based** (train: до марта 2026; val: апрель–июнь 2026), чтобы исключить утечку будущих решений в обучение.

### 4.3. Bias Analysis (анализ предвзятости данных)

| Выявленное смещение | Природа | Последствие | Мера |
|---------------------|---------|-------------|------|
| **Дисбаланс направлений**: финансы ~42% записей КБ, производство ~8% | Историческая активность обращений | Recall по «редким» направлениям ниже; риск систематически худшего сервиса для части команд | Per-direction hit rate в мониторинге; oversampling редких направлений в fine-tune |
| **Стилевое смещение авторов** | Записи КБ писали старшие инженеры (формальный стиль), запросы младших операторов — разговорный | Поиск хуже «слышит» формулировки новичков | Fine-tune на реальных парах (запрос → решение); семантический кэш уровня 2 |
| **Временной сдвиг** | Часть решений относится к старым версиям ERP | Устаревшие рекомендации при апгрейдах | Дрейф-детекция (PSI > 0.2) → переобучение; поле версии ERP в payload чанка |
| **Признаки пользователя исключены** | Имя, отдел, локация пользователя сознательно не участвуют в поиске/ранжировании | Защита от дискриминации по группам пользователей | Фиксация в Model Card + код-ревью фич |
| **Унаследованные смещения базовых весов** | Претрейн Qwen выполнен на внешних корпусах | Непредсказуемое поведение на редких конструкциях языка | Ограничение домена (RAG-only), оценка faithfulness, degraded-fallback |
| **Не измеряемое** | Сленг отдельных команд, опечатки, смешанные языки в выборке представлены недостаточно для честной оценки | Возможны необнаруженные провалы качества | Канал обратной связи (dislike) → ручная валидация → пополнение датасета |

### 5.2. Fairness — метрики справедливости

Для retrieval-системы справедливость определяется как **равенство качества сервиса между группами пользователей**, а не как demographic parity классификатора. Группы: направления поддержки (finance / logistics / production / master-data), стаж оператора (< 1 года / опытные), канал доступа.

| Метрика справедливости | Определение | Цель / порог |
|------------------------|-------------|--------------|
| **Per-direction hit rate** | Recall@10 по каждому направлению | ≥ 0.6 в каждой группе; **разрыв между группами ≤ 10 п.п.** (аналог equalized odds) |
| **Parity доли degraded** | Доля `status: degraded` по группам | Разрыв ≤ 5 п.п. |
| **FP дедупликации** | Полезная запись отклонена как дубликат (cosine > 0.92) | ≤ 5% по каждому направлению — защита от «замывания» редких направлений |
| **Dislike rate по направлениям** | Доля отрицательных отзывов операторов | ≤ 30%, разрыв между направлениями ≤ 10 п.п.; направление-специфичное падение accuracy > 10% — триггер отката канарейки |

**Текущие значения по направлениям (hit rate):** finance 0.84, logistics 0.79, master-data 0.77, **production 0.71** — разрыв 13 п.п. превышает целевой. Это осознанное зарегистрированное ограничение: в плане — oversampling направления production при следующей итерации fine-tune (v1.3) и приоритетное наполнение КБ.

**Процедура контроля:** fairness-отчёт строится автоматически ежемесячно + обязателен на шаге 3 канарейки (ML-метрики, Argo Rollouts). Нарушение любого порога = остановка раскатки или триггер переобучения.

## 6. Ethical Considerations (этика и подотчётность)

- **Подотчётность (Ownership Matrix):** каждая версия модели имеет ML Owner (технические метрики, дрейф, переобучение) и Business Owner (бизнес-качество, приоритеты валидации). Model Card подписывается обоими и пересматривается ежеквартально и при каждом релизе.
- **Логирование решений для аудита:** каждый запрос фиксируется асинхронно в PostgreSQL (не блокирует ответ): `trace_id`, `X-User-Id` (только идентификатор, без ПДн), SHA256(query+filters+config), найденные ID записей, статус (ok/degraded/empty), версия модели (MLflow run_id), обратная связь. Audit Store — append-only; retention: hot 30 дней / cold (сжатый архив) 180 дней / удаление по требованию комплаенса.
- **Возможность обжалования:** кнопка «дизлайк» в интерфейсе ERP и любой спор по рекомендации создают запись в очереди ручной валидации админ-панели; SLA разбора — 5 рабочих дней. Решение администратора фиксируется и попадает в датасет дообучения.
- **Персональные данные:** ПДн маскируются до эмбеддинга; в логах и кэше — только идентификаторы и хэши. Все вычисления внутри контура компании (152-ФЗ).
- **Человек в контуре:** модель никогда не выполняет действий в ERP; финальное решение — за оператором. Поэтому уровень риска — Limited, а не High.

# Часть 2. FinOps: анализ превышения бюджета и план Cost Optimization

## 9. Контекст и допущения

- Продуктивный контур развёрнут в частном облаке провайдера (IaaS): кластер K8s, пулы нод general (3× 8CPU/32Gi) и gpu (2× A100), персистентные тома, сеть — всё оплачивается по счёту провайдера. Данные не покидают выделенный сегмент (ограничение «без внешних SaaS/API» соблюдается).
- Dev/Staging и ML-эксперименты (fine-tune, дистилляция, нагрузочные прогоны) — в том же облаке, на синтетических/обезличенных данных.
- **Бюджет: 4.0 млн ₽/мес. Счёт за июль 2026: 6.0 млн ₽ (+50%).**

## 10. Структура счёта

| Категория | План, млн ₽ | Факт, млн ₽ | Δ, млн ₽ | Комментарий |
|-----------|------------|-------------|----------|-------------|

## 11. Анализ причин перерасхода

### 11.1. Забытые GPU-инстансы в dev/staging (+1.15 млн ₽/мес)

- Dev- и staging-версии `qwen_serving` (LLM на A100) подняты **24/7**, хотя нагрузка существует только в рабочие часы (планировалось ~176 ч/мес, фактически 720 ч/мес).
- Jupyter-поды исследователей с запросом `nvidia.com/gpu: 1` не удаляются после экспериментов; типичная утилизация GPU в пуле dev по DCGM-метрикам — **< 10%**.
- Ночные/выходные прогоны fine-tune остаются висеть после завершения DAG (Airflow worker не освобождает GPU-под).
- Нет ни алертов на простой, ни scale-to-zero: KEDA-триггеры настроены только для AI Service в проде.

### 11.2. Хранение без TTL (+0.55 млн ₽/мес)

| Источник роста | Что происходит |
|----------------|----------------|
| Decision/audit log в PostgreSQL | Пишется каждый запрос (промпты, ответы, метаданные) **без retention policy** — ~40 ГБ/мес и растёт; PV расширялся дважды |
| Prometheus | Retention ad hoc увеличен с 30 до 90 дней «на всякий случай», без downsampling |
| MinIO | Каждый чекпоинт каждого fine-tune и все промежуточные датасеты сохраняются навсегда; ежедневные снэпшоты Qdrant копятся без ротации |
| Harbor | Образы всех сборок без retention-политики |
| Бэкапы | Полные ежедневные копии PG/Qdrant поверх снэпшотов, без lifecycle |

### 11.3. «Слишком умная модель» для простых задач (внутри прод-GPU и скрыто ограничивает экономию)

- Qwen3.5-35B обрабатывает **все** запросы, включая простые типовые («где сбить кэш документа», «как reset пароля») — это ~60% потока по анализу decision log.
- Prefix caching системного промпта заявлен в архитектуре, но в текущем релизе vLLM запущен **без** `--enable-prefix-caching`; батчинг в асинхронном пути не включён → утилизация GPU низкая, а нужное количество GPU-часов на запрос — завышенное.
- Semantic cache даёт hit ratio 38% вместо целевых 60–80%: TTL точных совпадений занижен относительно фактической повторяемости запросов из ERP.
- Отсутствуют `max_tokens`-лимиты на генерацию и token budgeting: отдельные деградировавшие циклы ERP-polling порождали повторные дорогие генерации.

### 11.4. Оверпровижининг CPU (+0.20 млн ₽/мес)

- `requests.memory` подов установлены «с запасом» и не пересматривались с MVP; фактическое потребление 30–40% от запрошенного.
- Airflow KubernetesExecutor-воркеры не масштабируются в ноль; staging-окружение постоянно полностью поднято.

### 11.5. Процессные причины (корневые)

- Нет атрибуции затрат: ресурсы не размечены (labels namespace → команда/окружение), стоимость не показывается командам (showback), бюджеты и алерты на аномалии не настроены. Перерасход обнаружился только по счёту, а не по метрике.

## 12. План Cost Optimization

### Этап 0. Быстрые победы (недели 1–2, без изменения архитектуры)

| № | Мера | Реализация | Оценка эффекта |
|---|------|------------|----------------|
| 1 | **Schedule-based scale-to-zero для dev/staging** | KEDA cron-триггеры / kube-downscaler: GPU-пулы dev и staging живут 08:00–20:00 пн–пт (~176 ч/мес вместо 720); ночью и в выходные реплики LLM = 0 | до −1.2 млн ₽/мес (консервативно **−0.90**) |
| 2 | **Детектор простоя GPU** | Алерт Prometheus (DCGM `utilization < 10%` в течение 4 ч) + автоприостановка пода; еженедельный отчёт «брошенные GPU-ресурсы» | предотвращает возврат проблемы |
| 3 | **TTL для всех хранилищ** | PG: партиционирование audit-log по месяцам, hot 30 д → cold (сжатие) 180 д → delete; Prometheus: retention 15 д + downsampling правил; MinIO lifecycle: не-продакшн чекпоинты — удалить через 14 д, датасеты → cold tier через 30 д, снэпшоты Qdrant — 7 дневных + 4 недельных; Harbor retention: последние 10 тегов на паттерн; бэкапы: инкрементальные + GFS | **−0.40** |
| 4 | **Rightsizing CPU/RAM** | VPA в recommend-mode по данным Prometheus за 30 д; приведение requests к P95 факта; scale-to-zero для Airflow-воркеров вне расписания | **−0.15** |

### Этап 1. Архитектурные меры (месяцы 1–2)

| № | Мера | Детали | Оценка эффекта |
|---|------|--------|----------------|
| 5 | **Model Tiering / Cascading Router** | Классификация сложности запроса (правила + лёгкий классификатор по длине/категории/истории): простые запросы (~60%) → малая модель Qwen3-8B (INT4), сложные → 35B; при низкой уверенности/низком score retrieval — каскад вверх к 35B | −40–50% GPU-часов генерации (**−0.55** совместно с №6–7) |
| 6 | **Distillation (дистилляция)** | Студент 7–8B обучается на парах (запрос → ответ учителя 35B) из decision log за 6 мес; целевая замена 35B на ≥ 80% трафика; обе модели в INT4 помещаются в существующий GPU-пул **без расширения** | снижение стоимости на успешное решение; качество контролируется quality gates (§13) |
| 7 | **Включение префикс-кэша и батчинга** | vLLM `--enable-prefix-caching` (KV-cache системного промпта ~2К токенов), dynamic batching в async-пути (окно 0.5 с, max 32) — уже спроектировано в highload-архитектуре, но не включено | −20–30% времени GPU на запрос |
| 8 | **Повышение cache hit ratio 38% → 60%+** | Анализ повторяемости в decision log → корректировка TTL точных совпадений (до 24 ч) и порога семантического уровня кэша; каждый hit — ноль вызовов LLM | прямое снижение GPU-часов |
| 9 | **Spot/preemptible для batch-задач** | Fine-tune embedding, дистилляция, batch-оценки — на прерываемых GPU-инстансах с чекпоинтингом (Airflow DAG уже пишет чекпоинты); допустима потеря инстанса без ущерба прод | **−0.10** на оставшихся обучающих задачах |
| 10 | **Token budgeting** | Жёсткие `max_tokens` на генерацию, лимиты на пользователя/тенанта, дедупликация идемпотентных запросов (X-Idempotency-Key уже есть на Gateway) | защита от зацикливаний и повторов |

### Этап 2. Операционная зрелость (квартал)

| № | Мера | Детали |
|---|------|--------|
| 11 | **Разметка и showback** | Labels `team`, `env`, `service` на всех namespaces/PV; дашборд юнит-экономики в Grafana: **₽/1К токенов, ₽/успешное решение, ₽/MAU**; ежемесячный showback владельцам команд |
| 12 | **Бюджеты и алерты** | Бюджет на категорию счёта; алерт при отклонении week-over-week > 10% или прогнозе месяца > бюджета — раньше, чем придёт счёт |

## 13. Баланс цены и качества (контроль деградации)

Оптимизация не считается успешной, если она снижает качество сервиса: дешевле считать **₽/успешное решение**, а не голый счёт. Для каждой меры определены quality gates (переиспользуются rollback-триггеры канарейки из `docs/service-iac.md`):

| Gate | Порог | Что при нарушении |
|------|-------|-------------------|
| Retrieval hit rate | ≥ 0.6, падение > 10% по направлению | Откат канарейки, возврат к 35B |
| Dislike rate | ≤ 30%, разрыв по направлениям ≤ 10 п.п. | Откат + анализ |
| Faithfulness студента (после дистилляции) | ≥ 0.90 на контрольной выборке | Студент не заменяет учителя, остаётся только маршрутизация |
| Latency P99 | ≤ 3 с (поиск) / ≤ 5 с (генерация) | Откат конфигурации vLLM |
| Доля degraded | ≤ 2% | Откат |

Раскатка каждой оптимизации (новая малая модель, дистиллят, изменения vLLM) — через тот же Canary-процесс Argo Rollouts (1% → 5% → 25% → 100%) с автоматическим откатом по метрикам. Каскадный роутер гарантирует graceful degradation: сомнительный случай всегда уходит к большой модели, SLA пользователя не ухудшается.
